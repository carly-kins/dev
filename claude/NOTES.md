# Claude Code setup — what's here and why

This folder is the source of truth for my Claude Code config. `~/.claude/` holds symlinks
into it (same pattern `install.sh` already uses for `.oh-my-zsh-custom`), so this is what
survives a `git clone` onto a new machine and what actually gets edited.

**Source:** adopted 2026-09-25 from a colleague's shared setup
(`~/Desktop/claude-setup-share`, her "Cory's Claude Setup" Confluence writeup). Not copied
wholesale — see decisions below.

## Layout

| Path here | Symlinked at | What |
|---|---|---|
| `settings.json` | `~/.claude/settings.json` | Permissions, enabled plugins, statusline, hooks wiring (company-only plugins/marketplaces split out — see below) |
| `settings.company.json` | *(not symlinked — layered in via a shell alias, see below)* | Gitignored. Reingold-only `enabledPlugins`/`extraKnownMarketplaces` entries |
| `CLAUDE.md` | `~/.claude/CLAUDE.md` | Global preferences (see file for full content) |
| `CLAUDE.company.md` | *(not symlinked — imported by `CLAUDE.md`)* | Gitignored, machine-local. See its own note below. |
| `templates/` | `~/.claude/templates/` | `plan-doc.html`, `session-dashboard.html` working-doc templates, themed Catppuccin Mocha (see below) |
| `skills/close-out/` | `~/.claude/skills/close-out` | End-of-ticket sweep |
| `skills/plan-walk/` | `~/.claude/skills/plan-walk` | Gated step-by-step plan delivery |
| `skills/resume/` | `~/.claude/skills/resume` | Dashboard-based session resume |
| `skills/i-have-adhd/` | `~/.claude/skills/i-have-adhd` | Custom hand-written skill (moved here 2026-09-25 from `~/.agents/skills/`, where it had no recorded source — it was never an `npx skills` package, so now it's treated as mine) |
| `hooks/commit-guard.sh` | `~/.claude/hooks/commit-guard.sh` | Blocks `git add`/`git commit` from Claude |
| `hooks/notes-guard.sh` | `~/.claude/hooks/notes-guard.sh` | Blocks notes docs (dashboard/parking-lot) from being written into a repo |
| `statusline.sh` | `~/.claude/statusline.sh` | Terminal status line |
| `parking-lot.sh` | `~/.claude/parking-lot.sh` | Read/append layer for the parking-lot HTML |
| `notes-index.py` | `~/.claude/notes-index.py` | Regenerates a findable index of a project's notes dir |
| `install-plugins.sh` | *(not symlinked — run once)* | Bootstraps Claude Code's non-company plugins (superpowers, mattpocock-skills); runs `install-plugins.company.sh` if present |
| `install-plugins.company.sh` | *(gitignored, not symlinked)* | Reingold-internal marketplaces (`reingold-agent-plugins`, `-test`) + plugins (`aem`, `rg-delivery`) |
| `install-skills-cli.sh` | *(not symlinked — run once)* | Bootstraps the `npx skills` global skill packages |

**Deliberately NOT in this repo** (auto-managed caches, not hand-authored config):
`~/.claude/plugins/` (60MB+, Claude Code's own download of the 4 marketplace
plugins — regenerated by `install-plugins.sh` + normal use), `~/.claude/commands/*.md`
(shims generated by the separate `npx skills` CLI, regenerated by
`install-skills-cli.sh`), `~/.claude/skills/synced/` (pulled automatically from the
claude.ai account, no local action possible or needed), and everything under
`~/.claude/projects/`, `history.jsonl`, `cache/`, `sessions/`, and `~/.claude.json` at
`$HOME` (session/account state — the last one holds OAuth tokens, never touch it).

`~/.claude/settings.json` itself is **not** here — it's machine-local and references these
paths (`statusLine.command`, the two `PreToolUse` hook entries). If setting up a new
machine: clone this repo, run the symlink step below, then merge those `settings.json`
entries by hand (see git history of `settings.json` on the machine this was first set up
on, 2026-09-25, or just re-derive from `hooks/` + `statusline.sh` paths).

## New-machine bootstrap (not yet wired into `install.sh`)

Assumes Claude Code itself is already installed and you're logged in (`claude` on PATH,
`claude /login` done — that's what makes the org-tied `reingold-ai-skills` marketplace and
account-synced skills/plugins show up).

```bash
cd ~/dev   # this repo

# 1. Symlink config into place
ln -s "$(pwd)/claude/settings.json" ~/.claude/settings.json
ln -s "$(pwd)/claude/CLAUDE.md" ~/.claude/CLAUDE.md
ln -s "$(pwd)/claude/templates" ~/.claude/templates
ln -s "$(pwd)/claude/hooks" ~/.claude/hooks
ln -s "$(pwd)/claude/statusline.sh" ~/.claude/statusline.sh
ln -s "$(pwd)/claude/parking-lot.sh" ~/.claude/parking-lot.sh
ln -s "$(pwd)/claude/notes-index.py" ~/.claude/notes-index.py
ln -s "$(pwd)/claude/skills/close-out" ~/.claude/skills/close-out
ln -s "$(pwd)/claude/skills/plan-walk" ~/.claude/skills/plan-walk
ln -s "$(pwd)/claude/skills/resume" ~/.claude/skills/resume
ln -s "$(pwd)/claude/skills/i-have-adhd" ~/.claude/skills/i-have-adhd

# 2. Recreate the two gitignored company files by hand (CLAUDE.company.md,
#    install-plugins.company.sh — see notes on each above), then:

# 3. Bootstrap marketplaces/plugins and the npx-skills packages
./claude/install-plugins.sh        # runs install-plugins.company.sh too, if present
./claude/install-skills-cli.sh
```

## Decisions made adopting this (2026-09-25)

**Statusline** — installed as she wrote it (model · context % · cost · rate limits ·
parking-lot count · git branch · an AEM up/down dot, relevant since I use the `aem`
plugin), minus two things:
- Dropped the 💧 water-usage estimate segment entirely (own preference).
- Didn't merge in my old `user@host:dir` prefix from `statusline-command.sh` — kept it as
  a straight adopt of her version. `statusline-command.sh` is left in place, just no
  longer referenced by `settings.json`, in case I want to revisit.

**Hooks** — installed both. `commit-guard.sh` makes "I never stage/commit for you"
mechanical instead of just a prompted rule. `notes-guard.sh` keeps dashboards/parking-lot
out of repos.

**Skills** — installed `close-out`, `plan-walk`, `resume` as-is. No name collisions with
the `superpowers`/`mattpocock-skills` plugins I already have, but they're a *different*
planning paradigm (session dashboard + parking lot) from superpowers' own
`writing-plans`/`executing-plans` — pick one per task rather than mixing.

**`CLAUDE.md`** — built section-by-section, not copied wholesale (her own README said not
to). Kept: Subagent Model Routing, Usage Budget, Core Behavior (**as-is, including the
8-step ticket-execution gate and the no-AI-attribution rule** — this overrides the
harness's default commit/PR attribution line), Deterministic vs. Judgment Work, Context
Hygiene, Testing, Session Dashboard, Doc Conventions, Response Contract (defines the
"confidence line" that `plan-walk` refers to), Parking Lot. Adapted: "Which Plan System
When" (kept the coding-vs-non-code split, dropped her `thoughts/` folder and
`/create-plan`-style command references since I don't have that pipeline set up), "Where
Things Live" (kept only the rows for what's actually installed; template paths point at
`~/dev/claude/templates/...`, the real files, not the `~/.claude/` symlinks), Glossary
(trimmed to Session dashboard / Parking lot / NOTES dir — dropped Spec / Plan / RPI, which
belong to the delivery workflow below). Skipped entirely: **Delivery Workflow** (specs at
`docs/specs/`, her exact PR-description format, `/rg-delivery:spec-feature` — tied to her
repos' conventions; revisit if/when a repo I work in actually adopts a docs/specs/
convention).

**Company-process split (2026-09-25)** — the "Ticket execution guardrails" 8-step block
was pulled out of `CLAUDE.md` into `CLAUDE.company.md`, which is `.gitignore`d (see
`../.gitignore`) and pulled back in via a `@/Users/cwooten/dev/claude/CLAUDE.company.md`
import line in `CLAUDE.md`. Reasoning: that block is shaped around my employer's
ticket/branch/PR process, not general personal preference, so it shouldn't live in a
personal dotfiles repo. Two bullets that referenced "the ticket" in passing were
generalized to plain "the request" wording so `CLAUDE.md` stands alone without the import.

Two things confirmed against the official docs (code.claude.com/docs/en/memory), one
open question:
- **Confirmed:** relative `@import` paths resolve relative to the *file containing the
  import*, not cwd. Since `CLAUDE.md` is read through the `~/.claude/CLAUDE.md` symlink,
  it was genuinely unclear whether that means "relative to `~/.claude/`" (the symlink) or
  "relative to `~/dev/claude/`" (the real file) — docs don't address symlinked imports
  directly. Fixed by using an **absolute path** in the import instead of a relative one,
  which sidesteps the question entirely.
- **Confirmed:** both relative and absolute import paths are supported.
- **Unconfirmed:** what happens when the imported file doesn't exist (e.g. on a personal
  machine before `CLAUDE.company.md` is recreated there). Not documented by Anthropic;
  informal reports suggest it's silently skipped with no error, but treat that as
  likely-not-certain until actually observed. Low stakes either way — worst case is a
  one-time confusing message, not a broken session.

**To carry this to a new work machine:** recreate `~/dev/claude/CLAUDE.company.md` by hand
(it's gitignored, so `git clone` won't bring it) — and if the machine has a different
username, update the absolute path in `CLAUDE.md`'s import line to match.

**Template theme (2026-09-25)** — recolored both templates to Catppuccin Mocha, matching
the terminal/`glow` theme already in `.oh-my-zsh-custom/catppuccin.json`. `templates/theme.css`
is the single source of truth for the palette + the handful of rules genuinely shared
between both docs (body bg/color, links, code, selection); `templates/build.py` inlines it
between `BEGIN/END SHARED THEME` marker comments in each `.html` file. The shipped templates
stay fully self-contained (no `<link>` to theme.css at runtime) — only the two comment
markers reveal it's generated, so sharing a filled-in dashboard/plan doc with someone else
still works with zero extra files. **To change the theme:** edit `theme.css`, run
`python3 templates/build.py`, done — both templates update together. Also fixed
`notes-guard.sh`, which was blocking writes to the templates themselves (their filenames
contain "dashboard", tripping the personal-notes-doc check) — added an allowlist entry for
the `templates/` path itself.

**Settings split (2026-09-25)** — `settings.json` is a single live file Claude Code both
reads AND writes, so it can't use the `@import` trick CLAUDE.md uses. Checked the official
docs first (code.claude.com/docs/en/settings, .../plugins/loading): there's no global
`~/.claude/settings.local.json` equivalent — "local" scope is always project-scoped
(`<project>/.claude/settings.local.json`). What IS confirmed and does work at the global
level: the `claude --settings <file>` CLI flag adds another precedence layer that merges
**key by key** with `enabledPlugins` (confirmed in the docs; `extraKnownMarketplaces`
isn't explicitly documented the same way but behaves consistently in practice since our
base file has none of its own to conflict with).

So: the two Reingold `enabledPlugins` entries (`aem@reingold-ai-skills`,
`rg-delivery@reingold-agent-plugins`) and both `extraKnownMarketplaces` entries moved to
gitignored `settings.company.json`. A `claude` alias in `.oh-my-zsh-custom/templates/aliases.sh`
(already symlinked live as `~/.zshrc` → sources `aliases.sh`) adds `--settings
~/dev/claude/settings.company.json` automatically whenever that file exists, and is a
silent no-op when it doesn't (e.g. on a personal machine). **Known gap:** this only covers
`claude` invoked from an interactive shell — a GUI/IDE integration that launches the
`claude` binary directly by absolute path would bypass the alias and miss the company
plugins. Not solved here; revisit if that becomes an actual problem.

**Action needed once, right after this change:** open a new terminal (or `source ~/.zshrc`)
so the alias picks up — until then, a freshly-started `claude` won't have the `aem`/
`rg-delivery` plugins or the two Reingold marketplaces, since they were just removed from
the live (symlinked) `settings.json` and only come back via the alias.

**To carry this to a new work machine:** recreate `~/dev/claude/settings.company.json` by
hand (gitignored, won't come with `git clone`) using the shape above.
